# 实验结果 — 关键洞察

CSR-DMI 路径在 Core_Jtag_Chip 上**也坏了**，但坏的更早：第一次 [dm_read(DMCONTROL)](file:///home/lizeyu/eng/coralnpu/tape_out/coralnpu_test_utils/jtag_dmi_interface.py:339:2-343:16) 就返回 `rsp.op=0xBDF815B5`（垃圾），而 JTAG-DMI 路径前 4 个用例都正常工作。

```
CSR-DMI:  dm_request_halt → 第 1 次 dm_read 立即返回垃圾  (2.6 µs)
JTAG-DMI: pre-halt 全部正常 → halt 后 dm_read_reg(DCSR) 卡 BUSY  (120 µs)
```

## 由此得到的结论

1. **JTAG → DM bridge 本身不是 bug** — 4 个 PASS 用例（包括 abstract command path）证明了这点。
2. **问题是环境性的** — Core_Jtag_Chip 的 CSR-DMI 也坏，但 Core_Axi_Chip 的 CSR-DMI 工作正常。
3. **两条 DMI 路径在 Core_Jtag_Chip 上互相干扰** —— `kernel.dmReqArbiter` 的 round-robin 仲裁 + dmi_jtag 在 TAP idle 状态下可能仍然驱动 `req.valid` 的残留信号，让 in(0)/in(1) 仲裁出错；这能解释：
   - CSR-DMI 第一次就拿到错误响应（被 in(0) 的某个无效请求"窃听"）
   - halt 后 abstract command 的"BUSY"实际可能是 in(0) 持续 valid 但永远 ready=false → 仲裁 starve in(1)
4. **真正的 fix 方向**：在 Core_Jtag_Chip 里需要确保 dmi_jtag 的 dmi_req_valid 真的会回到 0（否则即使 JTAG 静止，也会持续 starve 仲裁器）；或者把 `dmReqArbiter` 改成"in(1) 优先"模式，避免 round-robin 在 in(0) 持续高时饿死 in(1)。
