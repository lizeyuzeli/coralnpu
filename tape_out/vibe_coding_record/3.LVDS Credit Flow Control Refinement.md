## 2. AsyncFIFO 用 Chisel `AsyncQueue` 替换的可行性

### 关于 Chisel 自带 AsyncQueue
`chisel3.util.AsyncQueue` 实际上是 **rocket-chip** 的 `freechips.rocketchip.util.AsyncQueue`（你 repo 里 [third_party/rocket_chip/BUILD.bazel](file:///home/lizeyu/eng/coralnpu/third_party/rocket_chip/BUILD.bazel:0:0-0:0) 已经有），不是 chisel 标库。它确实可综合，是工业用过的 Gray-code 指针 + 2FF 同步器实现，支持 FWFT。[hdl/chisel/src/bus/TlulFifoAsync.scala](file:///home/lizeyu/eng/coralnpu/hdl/chisel/src/bus/TlulFifoAsync.scala:0:0-0:0) 已经在用它，证明在本工程的 toolchain 下可用。

### 流片注意点
1. **Reset 跨域**：`AsyncQueue` 需要两个域各自的同步释放复位（async assert / sync deassert），即与你现在 `LvdsAdapterChip`/`Fpga` 里 `RstSync` 给出的 `core_aresetn` / `lvds_aresetn` 用法一致。两边复位**不能完全独立断言**——必须保证 FIFO 内部的 Gray 指针不会在一边 reset 时被另一边读到非法值；rocket 实现里通过 `safe=true` 做了 sink/source ready 抑制来处理这一点，建议保持 `safe=true`。
2. **Memory 推断**：rocket 的 `AsyncQueue` 默认用 `Mem`（推断成 distributed RAM/flop array，不会推断成你想要的 dual-port SRAM）。流片用 SRAM macro 时，综合工具一般不会自动替换。所以**生产路径仍需 SV BlackBox + dual port SRAM IP**。
3. **Reset 域与时钟门控**：DFT 上需要保证两边的 `te` / scan reset 处理一致，目前 SV 版本 `AsyncFIFO_RTL` 已有 `rstn_wrclk/rstn_rdclk` 两组复位，AsyncQueue 同样满足。
4. **Lint / CDC 检查**：流片前需要给 CDC 工具加 waiver / constraint（Gray-code 指针、2FF）；这两种实现都需要做。

### 修改方案
增加 `useChiselAsyncQueue: Boolean` 参数：
- `true`（FPGA / 验证 / 早期流片实验）：实例化 `AsyncQueue`，省掉 SV 依赖。
- `false`（最终流片）：保持现在的 `AsyncFIFOFwft` BlackBox 路径，方便后期换 dual port SRAM。

参数挂在 `LvdsAdapterChip` / `LvdsAdapterFpga` 上（或全局通过 `Parameters` 传入），[LvdsLink.scala](file:///home/lizeyu/eng/coralnpu/tape_out/hdl/chisel/src/coralnpu/LvdsLink.scala:0:0-0:0) 提供一个工厂 `def makeAsyncFifo(...)`。

## SDC 约束（针对异步 FIFO，无论 SV 版还是 AsyncQueue）

两条都需要：

```tcl
# 1. 声明两条时钟异步（最关键，告诉 STA 不要做跨域 setup/hold）
set_clock_groups -asynchronous \
    -group [get_clocks core_clk] \
    -group [get_clocks lvds_clk]

# 2. 对跨域路径（gray 指针 / 数据 RAM 输出）限定最大延迟，
#    避免被 -asynchronous 完全 false_path 掉而出现长 metastable 窗口
set_max_delay -from [get_clocks core_clk] -to [get_clocks lvds_clk] \
    -datapath_only <min(T_core, T_lvds)>
set_max_delay -from [get_clocks lvds_clk] -to [get_clocks core_clk] \
    -datapath_only <min(T_core, T_lvds)>

# 3. Reset 同步器路径设 false_path（你的 RstSync 第一级 flop 的 D 端）
set_false_path -to [get_pins -hier *RstSync*/*sync0*/D]
```

`AsyncQueue`（rocket）和你手写的 SV FIFO 都是 gray-code + 2FF，约束模板一致。`AsyncQueue` 内部已自动 `dontTouch` 同步器寄存器，集成到 SDC 里查找路径会更直观。

> 实操建议：流片时先生成 SDC 模板，让综合 / STA 跑一次 CDC report（DC 的 `report_clock_groups` / Genus 的 cdc 分析），看是否还有遗漏的 false_path/max_delay。

# 现状回顾

- 链路是单向 16B beat 的 LVDS（每侧 TX FIFO + RX FIFO，depth=8）。
- 帧：1 个 header beat（含 opcode + 元数据） + 可选 1 个 data beat。
- 当前流控：每 pop 一个 beat → 一个 1-bit GPIO pulse → 对面边沿计数 → +1 credit。**核心脆弱点**：脉冲一旦丢/合并，credit 永久漏。

# 目标

1. 流控走 in-band（LVDS 数据通道），脱离 GPIO。
2. **Credit 更新对单包丢失免疫**（PCIe-style：累计计数 + 周期上报）。
3. 普通帧用 timeout + 重传兜底丢包。

# 方案草案

## A. 帧格式扩展

复用 header 的 opcode 字段，新增一个**控制平面**类（暂叫 `M_CREDIT_UPDATE`），单 beat 无 data：

```
header[127:0]:
  [7:0]   opcode  = M_CREDIT_UPDATE
  [15:8]  reserved
  [N+15:16]  rx_consumed_total   // 累计已 pop 的 beat 数（mod 2^N）
  [...]      crc-ish 简易校验（可选）
```

`N` 选 8 bit 足够（mod 256；最大 in-flight 远小于 128，wraparound 不歧义）。

## B. 信令语义（关键设计点 1）

**累计计数 (cumulative) 而非增量 (delta)**：
- 每侧维护 `rx_consumed_total[N-1:0]`，pop 一个 beat 就 +1（自由 wrap）。
- credit 包带的就是这个绝对值。
- 对面维护 `last_seen_consumed`；收到包后 `freed = (new - last_seen) mod 2^N`，本地 `tx_credit += freed`，`last_seen := new`。
- **效果**：丢任意数量的 credit 包都没事，下一个到达的更新会一次性还回所有累积的 credit。

## C. 触发策略（关键设计点 2）—— 三选一/混合

| 策略 | 触发条件 | 链路开销 | credit 延迟 |
|---|---|---|---|
| **纯 timer** | 每 N cycle 一发 | 恒定低 | 高（≤ N） |
| **threshold-only** | 累计 ≥ M 个未发 credit | 突发高 | 视流量 |
| **PCIe 风格（混合）** | `pending ≥ threshold` **或** `timer 到` | 适中 | 低且有上界 |

我建议**混合策略**：
- `threshold = depth/2 = 4`：每攒够 4 个未上报 credit 立即发。
- `timer_period = 64 cycle`：定时兜底，覆盖低流量场景。
- 上报后清空 pending；timer 重置。

## D. Credit 包自身的占用问题（关键设计点 3）

credit 包自己也走 LVDS FIFO，会占 1 slot。若不特殊处理，会出现「0 credit → 发不出 credit 包 → 永久 0」死锁。

PCIe 用 DLLP 走独立 layer。我们这里没有第二层，方案：

- **方案 D1（推荐，简单）**：发送端 credit 包**不消耗** `tx_credit`，**接收端从 RX FIFO pop credit 包时也不计入 `rx_consumed_total`**。代价：接收侧的 RX FIFO 必须有 ≥1 slot 永远留给 credit 包 → 把对外暴露的 effective depth 设成 `kFifoDepth - 1 = 7`，预留 1 slot 给 credit。
- **方案 D2（更安全）**：物理上拆两个 RX FIFO（数据 / 控制各一个），TX 也独立两条流。代价：多一个 AsyncFIFO 实例化。
- **方案 D3**：credit 包共享 FIFO 但分配独立的「control credit pool」（depth=2 的独立计数）。

D1 实现最简单，D2 最干净。**倾向 D1**——FIFO 深度 8 砍 1 给控制平面，业务影响微乎其微。

## E. TX arbiter 优先级（关键设计点 4）

`LvdsTxArbiter` 现在仲裁 3 个 shim 的输出。credit 包应**插队优先发送**（不然 timer 到了还排在 burst 后面，credit 延迟无界）。但要**有上限**，避免控制包饿死数据：

- credit 包优先级 = 最高；
- 但 credit 包发送频率天然由 threshold/timer 限制（不会连发）。

够用了。

## F. 普通帧丢包 timeout（关键设计点 5）

这块**比 credit 重构复杂得多**，需要：
1. **每个 shim 加 sequence number**（4 bit 够用）。
2. **发送端保留 in-flight 副本**直到收到对应 response。
3. **接收端按 seq 去重**（处理重传重复）。
4. **每个 shim 自己的 timer**，超时则重发。
5. ACK：现有 RSP 包天然就是 ACK（请求-响应一一对应），所以请求端的 timeout/重传比较好做；但**响应方向的 timeout** 需要单独 ACK 包（或合到 credit update 里）。

**这是个不小的工作量**。我建议：
- **本次先做 credit 重构（A–E）**，让流控本身可靠。
- **timeout/重传单独立项**：得先定义清楚错误模型（位翻转？整包丢失？帧错位？），否则容易过度设计。链路是 LVDS 短距，实际 BER 极低，可能用 CRC 检错 + 简单 NACK 已足够，不一定要 PCIe 那么重的 replay。

# 一、AsyncFIFO 只做 CDC，credit 流控走 sync FIFO

这个分离是对的，目前的设计把两者混在一起：**AsyncQueue 的深度同时是 CDC 缓冲深度，又是 credit 池深度**，这两个本来是不同维度的需求：

- **CDC 深度**：只要够吸收 gray-code 同步握手延迟即可（2~4 拍足够）。改大 CDC 深度对面积/时序不利。
- **Credit 池深度**：决定「sender 可以连发多少帧不等 ack」，越大吞吐越高，但要更大的接收缓冲。这跟跨时钟域无关。

**正确分层（每个通道每方向）：**

```
TX 侧 (core_clk):
  TxArb → SyncFifo(深度 = 该通道 credit 池)
        → AsyncFifo(深度 ~2，CDC 用) → LVDS PHY

RX 侧:
  LVDS PHY → AsyncFifo(深度 ~2，CDC 用)
           → SyncFifo(深度 = 该通道 credit 池) → consumer
```

- `txCredit` 初始 = SyncFifo 深度（不管 AsyncFifo），credit 计数只追踪远端 SyncFifo 占用。
- AsyncFifo 永远不会满，因为 SyncFifo 下游 1 拍可以接 1 拍，AsyncFifo 上游也是 1 拍 1 拍来。

# 二、虚通道死锁 — 师兄说得对，但 4 通道是 overkill

## 死锁是怎么产生的（共享通道场景）

我们当前版本已经把 credit 拎出来了，但**req 和 rsp 还共享一个 data 通道**。这个组合仍然有死锁路径：

```
chip→FPGA 通道塞满了 chip 的 ibus_req/ebus_req/slave_rsp 混合
       ↓ chip 的 slaveEng 想把 slave_rsp 发出去（响应 fpga 之前的 slave_req）
       ↓ 但 TX FIFO 满（被自己的 ibus_req 占掉）→ slaveEng 阻塞
       ↓ slaveEng 不能 pop 下一个进来的 slave_req
FPGA→chip 通道塞满，同样情况
       ↓ 两边互相等对方的 rsp 出来，cycle，死锁
```

这是经典的"req 占用了 rsp 通道空间，rsp 出不去导致 req 处理停滞"的耦合。本质上 **rsp 对 req 不能有 buffer 依赖**。

## 为什么你师兄说要分通道，但 4 个不必须

**死锁规避的最小条件**：依赖图无环。Req → Rsp 是单向依赖（处理 req 才产生 rsp，rsp 是终点），所以只要 **req 和 rsp 不共享 buffer**，环就断了。**2 个数据通道（req | rsp）就够死锁安全。**

**师兄说的 4 通道**（`rreq | wreq+wdata | rdata | rsp`，或 `req | wdata | rdata | rsp`）是出于**性能 / HoL blocking** 考虑：
- 写数据 burst 大，会把读请求堵住 → 影响读延迟 → AXI 之所以 5 通道也是这个原因。
- "wdata 相当于 wreq" 的意思是：wdata 和它前面的 wreq 必须按 order 走，如果 wdata 大块堵在通道里，连带后面的 rreq 也堵住。

但**对我们这条链路**：
- 单 beat 数据（128 bit），无 burst（每个 wreq 就 header+1 beat data，固定 2 拍）。
- 每个 shim 单 in-flight，最大同时在飞的请求数 ≤ 3（ibus + ebus + slave）。
- HoL blocking 的代价微乎其微。

所以**对我们的场景，2 数据通道（req | rsp）+ 1 credit 通道 = 3 通道就够**，再分 rd/wr 是过度设计。

## 我之前 credit 拎出来到底解决了哪一类死锁？

只解决了一种特殊情况：
- 「credit 包共享 data 通道 → 通道满 → credit 包发不出 → credit 永远不回来 → 永久 0 credit」

这是 VC 概念的一个**实例**（credit 包是和 data 不同的 message class，必须有独立 buffer）。但更根本的 req/rsp 死锁我并没解决，是潜在的 bug。**现在 9 个测试通过只是因为流量小，没逼出 cycle dependency。**

## 完整架构（推荐）

每个方向 3 个通道，各自独立的 sync FIFO + 小 async FIFO + 独立 credit 池：

| 通道 | 内容 | 流控 |
|---|---|---|
| **req_ch** | `M_IBUS_REQ` / `M_DBUS_RD_REQ` / `M_DBUS_WR_REQ` / `S_RD_REQ` / `S_WR_REQ` | credit 池 A |
| **rsp_ch** | `M_IBUS_RSP` / `M_DBUS_RD_RSP` / `M_DBUS_WR_RSP` / `S_RD_RSP_OK` / `S_RD_RSP_ERR` / `S_WR_RSP` | credit 池 B |
| **credit_ch** | `M_CREDIT_UPDATE`（一帧同时携带 A、B 两个累计计数） | 不参与流控，发送端 timer/threshold 限速 |

每方向 3 async + 3 sync = 6 个 FIFO，单 LVDS PHY 上 3 路 mux/demux（按 opcode 分类）。

**依赖图（死锁分析）：**

```
X.req → Y.slave → Y→X.rsp_ch → X.master (terminal, sink)
                      ↓ rsp_ch 满？
                      由 X 端 master agent 接收，single in-flight，
                      消费后立即释放 → rsp_ch 一定能 drain。
Y.req → X.slave → X→Y.rsp_ch → Y.master (terminal, sink)
                      同上对称。
```

无环 → 死锁安全。

**credit 通道是否需要 credit？** 不需要。CreditTracker 用 timer + threshold rate-limit，频率上界 ≤ 1 frame / 4 cycles；接收端 1 cycle drain 1 个，永不溢出。即便溢出，累计计数语义天然容错（下一个补丁包追平）。

语法上深度可以=1，但**实际可用性**要看吞吐：

| 深度 | sync=3 时的稳态吞吐 | 说明 |
|---|---|---|
| 1 | ~1/(2·sync+1) ≈ 14% | 只能"乒乓"一拍发一拍等 |
| 2 | ~30% | 仍受同步握手限制 |
| **4** | ~57% | **及格线**，丢一些 BW 但 functional |
| 8 | ~85% | 接近满速 |
| 16 | ≈ 100% sustained | 完全跑满 |

原因：写指针经 gray code 同步到读端要 `sync` 拍才可见；下一个空槽信号回到写端再 `sync` 拍。round-trip ≈ 2·sync 拍。深度需 ≥ round-trip × bandwidth 才能不停顿。

**所以 async 至少 4，要满吞吐 8。** 我把推荐改成：

- **AsyncFifo（CDC）= 8**：满 BW，sync=3 默认。
- **AsyncFifo (ctrl) = 4**：低速即可。

# Sync 池深度 = 16

收到，credit 池 16，吞吐 margin 大、覆盖最坏情况下的 round-trip。

不过这里有个**总缓冲容量与 credit 初值的关系**要写清楚：

- `recv_sync_depth = 16`，`recv_async_depth = 8`，物理总缓冲 = 24。
- **保守做法**：`tx_credit_init = recv_sync_depth = 16`（不算 async，把 async 当 CDC pipeline 透明缓冲）。
- 不会 overflow 的证明：sync 抽 async 是 1 拍/拍 core_clk 域；sender 最多让 16 个 beat 在飞，全部进 recv_sync 也装得下；async 中途短暂残留 < async_depth 拍即被排空。

req 池和 rsp 池都按这个走。

# 仲裁：RR 公平

赞成。具体方案：

- **TX 侧**（lvds 域 3 路 mux）：`ctrl` 严格最高优先级（频率极低，免饥饿），`req`/`rsp` 之间 **`RRArbiter`**。Chisel 自带 `chisel3.util.RRArbiter`，最后一个被选中的下次降到末位。
- **mid-frame 锁**：每个数据通道（req/rsp）各自独立的 lvds-域 `txMidFrame` 寄存器，被 RR 选中后必须把当前 2-beat 帧打完才能换；ctrl 只能在两个数据通道都处于 frame 边界时插入。
- **Core 侧 TX 入口**：`reqArb = RRArbiter(numSources)`、`rspArb = RRArbiter(numSources)` 各自做 RR，分别接到 req-sync FIFO 和 rsp-sync FIFO。具体来说：
  - `reqArb.in`: chip 侧 `ibusShim.reqOut` + `ebusShim.reqOut`；fpga 侧 `slaveAg.reqOut`。
  - `rspArb.in`: chip 侧 `slaveEng.rspOut`；fpga 侧 `ibusAg.rspOut` + `ebusAg.rspOut`。
- **RX 侧 demux**（lvds 域）：按 opcode 三分，无仲裁问题。

# 总结

## 实施的虚通道架构

每方向 3 个独立通道，每通道独立 buffer + 独立 credit 池：

```
core_clk: TxArb → AsyncFifo(CDC, 8 entries) → ┐
core_clk: TxArb → AsyncFifo(CDC, 8 entries) → ├─ 3-way mux ──→ LVDS PHY
core_clk: CT  → AsyncFifo(CDC, 4 entries) → ┘
                                       (ctrl > RR(req,rsp), frame-aligned)

LVDS PHY → 3-way demux ──→ AsyncFifo(8) ─→ SyncFifo(16, credit pool) → reqDisp → slaveEng
       (by opcode, expect-data) → AsyncFifo(8) ─→ SyncFifo(16, credit pool) → rspDisp → ibus/ebusShim
                                              → AsyncFifo(4) ─→ SyncFifo(2)         → CreditTracker
```

## 关键参数

| 参数 | 值 |
|---|---|
| AsyncFifo 数据通道深度 | 8（满吞吐 sustained） |
| AsyncFifo ctrl 通道深度 | 4 |
| SyncFifo req 深度 | 16 |
| SyncFifo rsp 深度 | 16 |
| SyncFifo ctrl 深度 | 2 |
| `tx_credit_init` (req) | 16 |
| `tx_credit_init` (rsp) | 16 |
| TX 仲裁 | ctrl 严格优先 > RR(req, rsp) |
| 帧对齐 | 各数据通道独立 mid-frame 状态 |

## 死锁保证

**req → rsp 单向依赖**：req 通道处理产生 rsp，rsp 通道是 sink（terminal），不会反向阻塞 req。两通道独立 buffer + 独立 credit，没有共享资源依赖环。

**ctrl 通道独立**：credit 帧不消耗 data 通道 credit，永远可发，杜绝"0 credit→无法返还 credit→死锁"。

## CreditTracker dual-pool

- 单一组合 credit-update 帧同时携带 `req_consumed_total` (id 字段) + `rsp_consumed_total` (addr 低 8 位)
- 累计计数器 mod 2^8，丢任何数量的 update 帧都能下次自动追平
- 触发条件：`(req_pending ≥ 8) ∥ (rsp_pending ≥ 8) ∥ (timer 64 cycles && 任一 pending)`

# Timeout/重传实现完成

## 设计概览

每个 master 侧状态机（chip `LvdsIBusShim`、chip `LvdsEBusShim`、FPGA `LvdsFpgaSlaveAgent`）新增一组寄存器：

```
timer        : 在 wait-rsp 状态计数
retryCnt     : 已用重试次数
pendingDrain : 已放弃但响应可能仍在路上的请求数
```

## 时序行为

```
sIdle → sReqOut → fire → sWaitRsp ┬─ rspIn.fire(!stale) → 正常 → sPresent
                          ↑       ├─ timer == 4096 && retry < 3 → retryCnt++, 
                          │       │   pendingDrain++,重发同一帧 → sReqOut
                          │       └─ timer == 4096 && retry == 3 → 
                          │            pendingDrain++, resp = SLVERR (2),
                          └────────── 跳到 sPresent/sDone(返回 fault)
```

**迟到响应处理**：`rspIn.ready := inWait || (pendingDrain > 0)`。任一状态下，若 `pendingDrain > 0`，先把 `rspIn.fire` 当作"消化历史遗留响应"，`pendingDrain--`，状态机不消费它。彻底避免迟到响应被错挂到下个事务。

## 错误响应语义

- **chip IBus**：`respReg := 2.U` （AXI SLVERR），下游 `sPresent` 拉 `io.ibus.fault.valid` 通知 core
- **chip EBus**：`respReg := 2.U`，`sDone` 拉 `io.ebus.fault.valid`
- **FPGA Slave**：`readOk := false.B` → 对读触发 `io.fabric.readData.valid` 但内容为 0；对写 `io.fabric.writeResp := false.B`（AxiSlave 看到这个就生成 SLVERR）

## 常量（`LvdsLink`）

```scala
val kTxTimeoutCycles: Int = 4096
val kTxMaxRetries: Int   = 3
val kTxTimerWidth: Int   = log2Ceil(kTxTimeoutCycles + 1)  // 13
val kTxRetryWidth: Int   = log2Ceil(kTxMaxRetries + 2)     // 3
```

后续 tune 只需改 `kTxTimeoutCycles` / `kTxMaxRetries` 两个常量。
